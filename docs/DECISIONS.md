## Decided 2026-10-07 (PHASE 06 notifications — do not re-litigate; reverse by new entry here)

| ID | Decision | Detail |
|---|---|---|
| D44 | A notification's tracking link carries the stored token hash, not a raw token | Only `sha256(token + ORDER_TRACKING_SECRET)` is stored (`orders.tracking_token_hash`), so a message sent for a status *after* placement has no raw token to rebuild the checkout link with. The message link therefore uses the stored hash as its capability — the same bearer value, held in the same service-role-only row and delivered only to that customer's phone — and `getTrackedOrder` accepts it as an alternative to the raw token, compared in constant time. The raw random token is unchanged and still the primary link. Rejected alternatives: storing the raw token (plaintext capability), or adding a `tracking_url` column (no DB access this session — the phase ships disabled, and the capability needs no schema). |
| D45 | PHASE 06 adds no notification columns and no new status values | Retry backoff is derived from `created_at` + `attempts` (`[0, 5, 10, 20, 40]` minutes, `MAX_ATTEMPTS=5`) so `notifications_queue_idx` still drives the scan without a `next_attempt_at` column; a replayed/overlapping cron is stopped by an atomic compare-and-swap on `attempts` (no `sending` status needed). Exhausted retries stay `failed` with a `— retries exhausted.` suffix in `last_error` rather than a `failed_permanent` value the existing check constraint forbids. The dev-only `console` notifier (selected by `notifications.whatsapp.provider='console'`) exists solely so the send pipeline can be exercised without a provider; it refuses to run when `NODE_ENV==='production'`. Upgrading WAHA later is one adapter file + one settings row (spec §4). |

## Decided 2026-10-08 (hydration + verification conventions — do not re-litigate; reverse by new entry here)

| ID | Decision | Detail |
|---|---|---|
| D46 | A client-only value MUST be gated by `useHydrated()` **inside the component that renders it** | Any value the browser derives on its own — the cart count from the `refreshCart` server action, a device-local list, a `Date`-derived string — can arrive *while React is still hydrating*. Swapping such a text node mid-hydration is exactly React `#418` ("server rendered text didn't match the client"), which is what a non-empty cart caused on every storefront route until 2026-10-08. The fix is the shared hook `src/lib/storefront/use-hydrated.ts` (`useSyncExternalStore`; React uses the server snapshot during hydration and switches afterwards), applied in the rendering component — `Header` (badge + `aria-label`), the cart page's priced lines, `AccountView`. **A provider-level flag does not work**: the header lives inside a `<Suspense>` boundary that can hydrate *after* the provider's effect runs, so a `mounted` state set in `CartProvider` still let the badge change mid-hydration (measured — the first attempted fix did not remove the error). Do not "fix" this by suppressing the warning or by hardcoding a value: gate it and let the count land on the next render. |
| D47 | Verification opens every admin route, including detail screens, with real row ids | `/admin/products/<id>` shipped returning **500** (a plain function passed into a client component across the RSC boundary) while every "admin screens open" check passed — because those checks opened the *index* screens only, and the product editor is the screen the owner actually uses for price/stock/photos. `.tmp/phase10/admin-route-sweep.mjs` now walks **every** `page.tsx` under `src/app/admin`, resolving `[id]` segments from a real row, and fails on a 5xx, an empty shell, or a missing admin chrome. Run it after any change to an admin page or its client components. Same rule for the storefront: a screen is not "verified" because the route that links to it renders. |
