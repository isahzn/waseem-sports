# PHASE 06 — Notifications
**Precondition:** D4 answered per channel AND provider docs researched (VERIFY). No provider chosen => build outbox + interface + a dev "console" notifier only.
## Tasks
1. `Notifier` interface + provider adapters chosen by settings/env. Email first if provider is ready; SMS next; WhatsApp only via official business API/approved provider.
2. Outbox: enqueue on order events (placed, confirmed, processing, shipped, delivered, cancelled) with `dedupe_key = orderId:event:channel`. Skip email when no email; skip gracefully when channel unconfigured (`status='skipped'`).
3. Cron route (auth by `SCHEDULED_JOBS_SECRET`): send queued/failed with capped retries and backoff; record `last_error`; never throw into order flow.
4. Templates (plain, short, include order number + tracking link). Admin: notification history per order + "resend" (rate-limited, audited).
5. Password-reset email via Supabase SMTP is separate — verify it works.
## Acceptance
- Provider down => order fine, notification failed with error, retried later, no duplicate sends on retry/replay.
- No message leaks another customer's data; tracking token only in that customer's link.

## Execution record — 2026-10-07 (built + verified; **ships disabled**, live WAHA delivery NOT proven)

**Scope built (all of it behind a disabled-by-default provider).** The `Notifier` seam and the settings/env-driven registry (`src/lib/notifications/`): `types.ts` (interface), `events.ts` (event catalog + toggle keys), `recipients.ts` (Sri-Lankan-aware normalisation to WAHA `chatId`), `templates.ts` (DB-backed `notifications.templates.<event>` with built-in defaults and total placeholder rendering), `config.ts` (`resolveChannel` — `waha`|`console`|`none`, kill switch, per-event toggles), `providers/waha.ts` (send + session/QR + inbound HMAC verification), `providers/console.ts` (dev-only), `outbox.ts` (claim → render → send → mark, capped retries, backoff, outbound rate limit, admin reads). Routes: `/api/cron/notifications` (GET/POST, `SCHEDULED_JOBS_SECRET` as bearer / `x-cron-secret` / `?secret=`; 503 when unset) and `/api/webhooks/waha` (HMAC over the **raw body** before parsing; 401 for unsigned/wrong/missing key; stores in `webhook_events`, replay no-op). Admin: `/admin/settings/whatsapp` (channel status panel, session/QR panel, editable numbers, per-event toggles, templates, kill switch, session actions, rate-limited+audited test send) and `/admin/notifications` (counts, filters, history, per-row resend/retry + retry-all, rate-limited + audited), plus a Notifications section on the order detail page and nav entries. The outbox writer (`src/lib/orders/notify.ts`) now resolves the real channel config, honours per-event toggles, and records a plain-language `skipped` reason when the channel is unconfigured or switched off.

**No schema migration was needed** (and none was possible from this session — no DB password / access token). Two capabilities were therefore designed into the existing tables instead of new columns: (1) retry backoff is derived from `created_at` + `attempts` (grow-only windows `[0, 5, 10, 20, 40] min`), so `notifications_queue_idx` still drives the scan and no `next_attempt_at` column exists; (2) a notification's tokenised tracking link carries the stored `tracking_token_hash` as the capability, because only the hash is stored (recorded as **D44**). Exhausted retries stay `failed` with a `— retries exhausted.` suffix rather than a new (`failed_permanent`) status value, which the status check constraint does not allow.

**Gates:** `npm run typecheck` 0 errors · `npm run lint` 0 errors / **5 pre-existing warnings** (unchanged from before this phase) · `next build` exit 0, with `/admin/notifications`, `/admin/settings/whatsapp`, `/api/cron/notifications` and `/api/webhooks/waha` in the route table.

**Live proof — 40/40 checks, real browser + real database + real server.**
- **No-provider path (production `node server.js`, no `WAHA_URL`/keys) — 17/17** (`no-provider`): a real checkout placed order `WS10030`, whose outbox row was exactly one `order_placed`/`whatsapp` row with `status='skipped'`, `provider='none'`, `last_error='No provider selected.'` and `dedupe_key=<orderId>:order_placed:whatsapp`; the order itself stayed `new`, reserved, with the DB shipping fee; the cron route refused callers with no secret and with a wrong secret (401) and, with the secret, returned `ok:true, sent:0` **without touching the row**; `/admin/settings/whatsapp` rendered all channels as “Not configured” (10 occurrences, no error) and the session panel explained WAHA is not set up; `/admin/notifications` listed the order's skipped row; an anonymous admin request redirected and leaked no order data; the tokenised link and the original raw token both opened the order, and a foreign token was a 404.
- **Provider-failure + console pipeline (dev server with `WAHA_URL` pointing nowhere) — 10/10** (`failure-console`): a configured-but-unreachable provider queued the row, the cron recorded `failed` with `last_error='WAHA unreachable: fetch failed'` **while the order stayed `new`/reserved**, and the next cron run **deferred** it (backoff, `attempts` unchanged) — no duplicate send. Switching to the dev-only console notifier sent exactly once (`sent:1`), recorded `sent_at`, and a replayed cron run sent nothing (`sent:0`, no duplicate row) — the atomic compare-and-swap claim is the no-duplicate guarantee. The rendered body (read from the server log) carried the order number **and** the tokenised `/order/<number>?t=` link. One order's capability could not open another order (404).
- **Inbound webhook — 6/6** (`webhook.mjs`, server started with `WAHA_HOOK_HMAC_KEY`): unsigned → 401, wrong signature → 401, correctly signed → 200 and stored **exactly once**, replay → 200 no-op.
- **Outbox completeness (`status-events`) — 7/7:** driving the real admin status form moved one order new → confirmed → processing → shipped → delivered and a second new → confirmed → cancelled, and each transition enqueued **exactly one** `skipped` row with the correct `orderId:event:channel` dedupe key (5 rows for the first order: `order_placed`, `order_confirmed`, `order_processing`, `order_shipped`, `order_delivered`; 3 for the second incl. `order_cancelled` — no duplicates). Shipping committed the unit (`on_hand -1`, nothing reserved) and cancelling released the reservation, so the order flow behaves independently of every notification.

**Test data:** orders, their cascaded notification rows, ledger rows, the temp shipping rule, webhook events and the provider setting were all removed; the linked dev project ends with `orders=0`, `notifications=0`, `notifications.*` settings rows `=0` and no held stock (`reserved=0` on every variant); demo stock distribution restored.
